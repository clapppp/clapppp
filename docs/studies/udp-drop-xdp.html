UDP 수신 처리와 XDP

2026-11-19 · 개별연구 12주차

수신 용량을 넘는 UDP 트래픽을 소켓에서 드롭할 때와 XDP에서 드롭할 때, 같은 코어에 CPU가 얼마나 남는지 비교한 실험이다.

지난 실험에서는 서버가 패킷당 20µs를 써서 수신 속도를 고정했는데, 수신 속도를 제한하는 프로세스보다 CPU 현황을 조회하는 프로세스를 두는 게 실험 목적에 더 맞다는 피드백을 받았다. 그래서 이번에는 서버는 bind만 하고 읽지 않아 도착한 패킷을 전부 드롭시키고, 남는 CPU를 전부 쓰며 카운터를 올리는 전용 프로세스 soak을 수신 코어에 함께 두었다. CPU를 받은 만큼만 카운터가 오르므로(FTQ 방식), 트래픽이 없을 때의 초당 증가량 대비 비율(soak_%)을 다른 작업에 남는 CPU로 삼았다. 지난번 bpftrace 측정은 IRQ · softirq 진입과 종료마다 vCPU0에서 프로브가 초당 10만 회 이상 실행되어 측정 비용만 vCPU0의 30%를 넘었는데, 카운터는 vCPU1의 모니터가 1초마다 읽도록 바꿔 xdp 4배의 soak_%가 11% → 48%로 제대로 잡혔다.

송신(호스트 CPU 1), 가상 NIC 역할을 하는 vhost-net(호스트 CPU 2), 수신 · 측정 대상(VM vCPU0 = CPU 3), 모니터링(VM vCPU1 = CPU 4)에 코어를 하나씩 고정했다. 지난번과 달리 vhost-net 프로세스도 전용 코어로 분리했다. CPU 3에서는 IRQ · softirq · XDP 수신 처리와 soak이 코어 하나를 나눠 쓴다. client는 UDP · IP · 가상 스위치를 거치는 send() 경로를 건너뛰고 AF_PACKET으로 tap(vnet0)에 프레임을 직접 보내며, 패킷은 tap → vhost-net(VM 버퍼 기록 · IRQ 주입) → virtio_net(IRQ · softirq) → (XDP) → 소켓 순으로 지난다. 64B UDP를 1 · 4 · 8배(50,000 · 200,000 · 400,000 pps)로 5초씩 보냈다.

XDP 프로그램은 virtio_net 수신 경로에 붙어, 패킷 주소 · 포트로 목적지 UDP 소켓을 찾고 수신 버퍼 사용량(rmem_alloc)과 크기(rcvbuf)를 비교해 버퍼가 이미 차 있으면 DROP, 아니면 PASS한다. 소켓이 없으면 PASS한다.

소켓 드롭(sock)에서 soak은 74.8% → 6.3%로 떨어졌다. 송신량이 늘수록 수신 처리가 CPU 3을 더 차지한다. XDP 드롭(xdp)에서는 80.9% → 40.0%로, sock 대비 1배 +6.1%p · 4배 +22.6%p · 8배 +33.7%p, 8배에서 남는 CPU가 6.3배였다.

IRQ 수는 두 방식 모두 초당 12~14만에서 멈췄다(IRQ당 패킷 1.0 → 3.3개). 1배에서 IRQ 1회 처리 시간은 sock 5.0µs(고정 3.3 + 패킷 1.7), xdp 3.8µs(고정 3.3 + 패킷 0.48)라 처리 시간이 원인이라면 sock은 약 20만 pps, xdp는 약 26만 pps부터 꺾여야 한다. 그런데 실제로는 둘 다 20만 pps에서 IRQ 13.9만 · 13.7만으로 이미 묶였다. 처리 비용이 다른데 같은 지점에서 꺾이므로 원인은 처리 시간이 아니라, 가상 NIC이 VM 드라이버로 전달하는 동작의 최소 간격(약 7µs)이다. 그보다 자주 온 패킷은 뭉쳐서 한꺼번에 전달된다.

4배에서 IRQ 한 주기(sock 7.2µs · xdp 7.3µs)를 나누면, 고정 3.3µs는 같고 패킷 처리가 sock 2.3µs(1.44개 × 1.58) → xdp 0.7µs(1.46개 × 0.48)로 줄어 soak 몫이 1.6µs → 3.3µs로 늘었다.
